# Архитектура

Выбрана слоистая архитектура для небольшого учебного приложения. Зависимости направлены внутрь: интерфейс обращается к прикладным сценариям, сценарии используют доменные правила и интерфейсы репозиториев.

| Слой | Ответственность | Не выполняет |
|---|---|---|
| Presentation / Controller | Ввод, отображение, разбор запроса, DTO и коды ответа | SQL и правила перехода статуса |
| Application / Service | Сценарии, координация, транзакции, проверка доступа | Рендеринг и детали конкретной БД |
| Domain | Сущности, инварианты, правила статусов и прав | Сеть, SQL и UI |
| Infrastructure / Repository | Хранение, маппинг, внешние адаптеры | Решение бизнес-политики |
| Database | Надёжное хранение и ограничения целостности | UI и бизнес-процессы |

## Ключевые компоненты
- `RequestController`: принимает команды; вход — запрос и идентификатор пользователя, выход — DTO или ошибка.
- `RequestService`: создаёт, назначает и переводит заявку; вход — команда, выход — заявка или ошибка правила.
- `AccessPolicy`: проверяет действие пользователя над объектом; выход — разрешение или отказ.
- `RequestRepository`: загружает и сохраняет заявки; выход — объект или список.
- `StatusPolicy`: проверяет переход статуса с учётом роли.

Структура: `src/presentation/`, `src/application/`, `src/domain/`, `src/infrastructure/`, `tests/unit/`, `tests/integration/`, `docs/`.

## Выбор и компромиссы
Слоистая схема проста для объяснения, прямо соответствует заданию и помогает изолировать бизнес-правила для тестов. Цена — дополнительная передача данных между слоями и риск избыточной абстракции. Модульный монолит по предметным областям расширять удобно, но границы сложнее определить для учебной работы. Микросервисы добавили бы сетевую и эксплуатационную сложность, поэтому не подходят текущему объёму.
