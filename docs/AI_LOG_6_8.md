# AI-журнал лабораторных работ 6–8

Записи содержат тестовые данные, без токенов, паролей и персональных данных.

## Лабораторная № 6

| Поле | Запись |
|---|---|
| Дата/этап | 10 октября 2026, планирование функционала и ревью сервисного слоя |
| Задача | Сопоставить требования с небольшими задачами реализации: создание, валидация, сохранение, поиск, статусы и архивирование. |
| Модель | gpt-6-luna, текущая сессия |
| Первый неполный промпт | «Сделай CRUD заявок на Python». |
| Недостатки первого запроса | Не указаны существующий проект и роли, не заданы SQLite, сервисный слой, правила статусов, ошибки и формат результата. |
| Улучшенный промпт | «Выступи разработчиком Python-проекта “Система учёта заявок”. На основе ролей заявитель/оператор/исполнитель/администратор предложи план реализации CRUD заявки с SQLite, repository/service слоями, обязательными полями, поиском, фильтрами по статусу и категории, назначением исполнителя, мягким удалением и проверкой переходов статуса. Не добавляй реальные секреты; ответ дай таблицей задач и критериев проверки». |
| Контекст | ТЗ, слоистая архитектура из ЛР № 3, минимальный функционал ЛР № 6; тестовые значения. |
| Результат | Выделены репозиторий, сервис, доменные правила статусов, валидация Pydantic и идемпотентный seed. |
| Проверка | Требования сопоставлены с кодом `app/db.py`, `app/repository.py`, `app/services.py`, `app/schemas.py`; схема БД содержит ограничения и индексы. |
| Доработка | Начальный общий CRUD-план уточнён мягким архивированием, таблицей истории и разрешёнными переходами. |
| Почему промпт/модель | Улучшенный запрос задаёт контекст, ограничения и проверяемый формат; модель выбрана для структурирования требований и ревью Python-кода. |
| Итог | В проект вошли слои DB/repository/service и UI-сценарии; решение проверяется запуском API и 14 запросами из `docs/requests.http`. |

## Лабораторная № 7

| Поле | Запись |
|---|---|
| Дата/этап | 10 октября 2026, проектирование REST-контракта |
| Задача | Спроектировать API заявок и проверить коды HTTP, схемы, фильтры и единый формат ошибок. |
| Модель | gpt-6-luna, текущая сессия |
| Промпт контракта | «Предложи REST-контракт для сущности Request в FastAPI: GET list/detail, POST, PATCH, DELETE/archive, справочники users/statuses/categories, query-фильтры q/status/category/priority, Pydantic-валидацию и коды 200/201/204/404/422. Отдели API от service слоя и не используй реальные секреты». |
| Промпт ревью | «Проведи критическое ревью этого контракта: обязательные поля, диапазоны, коды HTTP, единообразие ошибок, безопасность, удобство клиента и отсутствие дублирования бизнес-логики. Для каждого замечания дай решение принять/отклонить и причину». |
| Контекст | `app/main.py`, `schemas.py`, таблица требований ЛР № 7; демонстрационные идентификаторы. |
| Результат | Получены эндпоинты CRUD, справочники, `/health`, query-фильтры, OpenAPI, ошибки `404/422/500`. |
| Проверка | Файл `docs/requests.http` содержит 14 запросов, включая поиск, фильтры, создание, изменение, статус, ошибку валидации и 404. Swagger генерируется FastAPI. |
| Доработка | Принято замечание о мягком DELETE и вынесении переходов статуса в service; отклонено требование публичной аутентификации как выходящее за учебный минимум, ограничение описано в README. |
| Почему промпт/модель | Два запроса разделяют проектирование и критику; модель удобна для проверки интерфейса между слоями. |
| Итог | В проект вошли API-контракт, Postman collection и описание endpoint-ов; фактические скриншоты Postman нужно сделать после локального запуска. |

## Лабораторная № 8

| Поле | Запись |
|---|---|
| Дата/этап | 10 октября 2026, инфраструктурное ревью |
| Задача | Подготовить повторяемый Docker-запуск и проверить конфигурацию, порт, health-check, секреты и пользователя контейнера. |
| Модель | gpt-6-luna, текущая сессия |
| Промпт генерации | «Предложи Dockerfile для Python 3.12 FastAPI + uvicorn + SQLite. Укажи структуру app/main.py, requirements.txt и prototype, запуск на 8000, переменные окружения и health endpoint. Исключи секреты и локальные БД из build context». |
| Промпт ревью | «Проведи ревью Dockerfile: безопасность, размер, кеширование зависимостей, непривилегированный пользователь, порты, секреты и health-check. Предложи минимальные исправления и объясни их». |
| Контекст | `Dockerfile`, `.dockerignore`, `docker-compose.yml`, `.env.example`; секреты не передавались. |
| Результат | Dockerfile со slim-образом, отдельным пользователем `app`, ранним слоем requirements, портом 8000 и health-check; Compose с volume SQLite. |
| Проверка | Docker Desktop собрал образ командой `docker compose up --build -d`; `docker compose ps` показал контейнер `healthy`, порт `8000` опубликован. `Invoke-RestMethod http://localhost:8000/health` вернул `status=ok`, `database=ok`. Удалённый запуск отдельно не проверялся. |
| Доработка | Замечание о root исправлено: добавлен системный пользователь; замечание о секретах учтено через `.env.example` и `.gitignore`. |
| Почему промпт/модель | Ограничения явно связывают Docker с конкретной структурой Python-проекта; модель использована как инфраструктурный ревьюер. |
| Итог | Добавлены Dockerfile, Compose, `.dockerignore`, `.env.example` и инструкция с VPS-сценарием. Локальный контейнер проверен; URL удалённого деплоя отсутствует, так как сервер не предоставлен. |
