## Лабораторная № 1. Анализ требований

### Проблема и цель
Обращения, поступающие по почте, телефону и устно, сложно отслеживать: заявитель не знает, кто занимается проблемой, оператор теряет контекст, руководителю трудно увидеть просрочки. Система собирает обращения в одном месте, назначает статус и исполнителя, хранит комментарии и даёт искать историю.

Техническое задание в [`TZ.md`](TZ.md) содержит четыре роли, 12 функциональных и 6 нефункциональных требований, сценарии, сущности и критерии приёмки. Диаграмма — [`use-case.svg`](use-case.svg).

### AI-журнал
- **Задача:** получить черновик ролей, требований, сущностей и критериев для самостоятельной проверки.
- **Модель:** gpt-6-luna (модель текущей сессии; версия в интерфейсе не отображалась).
- **Промпт 1, свободный:** «Помоги разобрать предметную область системы учёта заявок: кто ей пользуется и что она должна уметь?»
- **Промпт 2, структурированный:** «Выступи системным аналитиком. Контекст: учебная система учёта заявок, где заявитель создаёт обращение, оператор назначает исполнителя, исполнитель обрабатывает, администратор управляет пользователями и категориями. Дай таблицы из четырёх ролей и прав, не менее 10 проверяемых функциональных требований в форме “Система должна…”, не менее 5 нефункциональных требований с измеримыми критериями, 5 сценариев, сущности и критерии приёмки. Не проектируй базу данных. Пометь предположения и не предлагай функции вне заданного контекста».
- **Почему такие промпты:** свободный запрос показывает широту ответа; структурированный задаёт контекст, формат и ограничения и исключает проектирование БД.
- **Почему модель:** текущая модель подходит для структурирования текста и проверки требований; отдельный выбор модели в интерфейсе не делался.
- **Результат:** типовые роли и функции поиска, назначения, комментариев и статусов.
- **Проверка:** сверены права ролей, путь заявки от создания к закрытию и соответствие пунктам методички.
- **Самостоятельная доработка:** заявитель ограничен собственными заявками; переходы статусов ограничены; производительности задан измеримый тестовый ориентир. Это допущения, которые следует согласовать с преподавателем/заказчиком.
- **Вывод:** структурированный промпт дал более проверяемый результат, однако права и метрики потребовали самостоятельного решения.

### Сравнение двух ответов
Свободная формулировка удобна для первичного обзора, но может пропустить обязательные критерии. Структурированная формулировка сразу покрывает роли, требования и приёмку в нужном формате. Для итогового ТЗ использован второй подход с проверкой соответствия методичке.

## Лабораторная № 2. Git

### Результат и workflow
Создан локальный репозиторий и осмысленные коммиты по этапам: исходная спецификация, архитектура, интерфейсный прототип, итоговая документация. Использованы ветки `main` и `develop`: в `develop` выполнено отдельное изменение, затем оно слито в `main`. Проверка: `git log --oneline --graph --all` и `git branch -av`.

`git merge develop` добавляет историю develop в текущую ветку. При конфликте нужно вручную отредактировать отмеченные файлы, проверить итог, выполнить `git add` и завершить merge-коммит. `reset --hard` удаляет локальные незакоммиченные изменения, `push --force` переписывает историю удалённой ветки; для обычного workflow они не нужны и не применялись.

### AI-журнал
- **Задача:** получить последовательность локального Git workflow и примеры сообщений коммитов.
- **Модель:** gpt-6-luna, текущая сессия.
- **Промпт:** «Для учебного проекта “Система учёта заявок” предложи безопасную последовательность команд Git: инициализация, main, пять осмысленных коммитов, develop, отдельное изменение, merge обратно в main. Дай .gitignore для Python. Для merge, reset и push --force объясни последствия; не включай удалённый URL и не предлагай destructive-команды без необходимости».
- **Почему:** ограничение локальным репозиторием позволяет не выдумывать URL; запрос требует объяснить последствия рискованных команд. Модель применена для инструкций и проверки workflow.
- **Результат:** отдельные этапы коммитов, ветка develop, игнорирование среды, кэша, локальных БД и секретов.
- **Проверка:** Git доступен; история и обе ветки созданы локально.
- **Доработка:** удалённый URL не задан, публикация не выполнялась. Локальные файлы БД игнорируются, SQL-скрипты-исходники этим правилом не затронуты. Конфликт не создавался; разобран сценарий его ручного разрешения.
- **Вывод:** команды Git следует выполнять с проверкой текущей ветки и состояния рабочего дерева.

## Лабораторная № 3. Архитектура

### Результат
Схемы и описание слоёв находятся в [`architecture/README.md`](architecture/README.md), диаграммы — `architecture.mmd` и `components.mmd`. Выбрана слоистая архитектура: presentation/controller → application service → domain и repository → database.

| Критерий | Слои | Модульный монолит |
|---|---|---|
| Простота | Высокая, ответственность очевидна | Средняя, нужно задавать границы модулей |
| Тестируемость | Хорошая при изоляции сервисов и репозитория | Хорошая при слабой связанности модулей |
| Расширяемость | Можно заменить адаптер хранения | Удобно развивать предметные области |
| Стоимость | Низкая | Средняя |
| Учебное соответствие | Наглядно показывает слои из задания | Наглядно показывает предметные границы |

Выбрана слоистая схема из-за объёма и соответствия заданию. Компромисс — дополнительная передача данных между слоями. Микросервисы создавали бы лишние сетевые и эксплуатационные расходы.

## Лабораторная № 4. Интерфейс

Откройте [`prototype/index.html`](../prototype/index.html) в браузере. Есть пять переключаемых экранов: вход, список, создание, карточка и редактирование. Поиск, статусный и категорийный фильтры, их сброс, сообщение пустого результата, проверка формы и подтверждение удаления работают. Авторизация и сохранение данных — демонстрационные заглушки.

| Экран | Назначение | Действия |
|---|---|---|
| Вход | Начать сессию | Ввести почту и пароль |
| Список | Найти и контролировать обращения | Искать, фильтровать, сбрасывать фильтр, открывать и создавать заявки |
| Создание | Зарегистрировать обращение | Ввести тему, категорию, описание; отправить или отменить |
| Карточка | Посмотреть детали, историю и обработку | Комментировать, назначить исполнителя, менять статус, редактировать, запросить удаление |
| Редактирование | Исправить содержание | Обновить тему/категорию/описание, сохранить или отменить |
